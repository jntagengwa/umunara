## Implementation decisions

- Stripe is the only added dependency, pinned to `22.6.1` in package and lockfile. The current official release is dated September 1, 2026 and includes request URL hardening. The installed SDK's API version is pinned explicitly to `2026-08-26.dahlia`. Node's default SDK constructor is imported as `StripeClient` and instantiated; no global key pattern is used.
- Checkout accepts only a strict `{ amountMinor, currency: 'USD', cadence }` DTO. Amounts are integer cents ($0.50–$999,999.99), including the browser's decimal-string conversion. USD preserves the existing US giving context; expanding checkout currencies requires a currency-aware input and settlement-fee policy. Cadence supports `one_time`, `monthly`, and `yearly`.
- The server creates a UUID per intent, attaches allowlisted amount/currency/cadence metadata to the session and its PaymentIntent or subscription, and supplies a provider idempotency key for SDK retries. The browser cannot choose identity, donor profile, return URLs, status, or metadata. No later mutation endpoint can edit this intent. The UUID is retained in provider metadata; Task 1 has no separate intent table and no new database schema was introduced.
- Return URLs come from a validated server-owned origin and fixed paths. Only a validated HTTPS `checkout.stripe.com` URL is returned. The form does not load Stripe.js, collect card data, or request application data from provider/database endpoints. It posts to `/api/v1`, then navigates to hosted Checkout. Return messaging never claims payment success.
- Dynamic payment methods remain enabled by omitting `payment_method_types`. Adaptive Pricing is disabled to preserve the intent's currency and amount. No `automatic_tax`, discounts, trial, or credit controls are enabled. Tax remains disabled; registrations would need separate explicit review before enabling collection.
- The webhook route calls `request.text()`. The SDK verifies the exact raw body with its default timestamp tolerance before event dispatch, provider reads, parsing into the ledger contract, or any ledger write. Missing/invalid/stale signatures return 400. Events must match the configured test/live environment and pinned snapshot API version; connected-account events are rejected. Unsupported event types and unrelated payments are acknowledged without ledger writes.
- Supported events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `payment_intent.succeeded`, `payment_intent.payment_failed`, `invoice.payment_succeeded`, `invoice.payment_failed`, and `charge.refunded`. Provider reads retrieve current financial state, so late success delivery retains existing cumulative refunds.
- One-time gifts use the PaymentIntent ID and its immutable creation time. Each recurring gift uses its invoice ID and invoice creation time. Subscription Checkout completion is ignored for ledger purposes; the invoice event owns the first payment as well as renewals. Refunds resolve back through Invoice Payments where necessary. This avoids creating a second gift for a refund or subscription Checkout notification.
- Normalization checks provider amount/currency against the intent metadata. Successful payments require an expanded paid charge and same-currency balance transaction; fees use the charge's processing fee and cumulative refunded amount comes from the charge. Full refunds retain fees and can produce negative net giving. Failed/pending payments have no fee/refund amounts. Partial/multi-payment invoices, credits/discounts, missing settlement fees, and FX settlement are refused with a retryable safe error rather than misstating giving. Disputes, refund fee adjustments, reinstatements and exceptional invoice reconciliation are not implemented in Task 2.
- Every handled verified delivery makes exactly one `recordEvent` RPC call. The database is the durable idempotency authority; there is no process-local production deduplication. The example plan's `upsertDonation` call-count assertion was adapted to Task 1's atomic envelope interface. Duplicate/stale results do not invalidate caches. Only an applied result invalidates `donations:summary:YYYY-MM` for the original gift's UTC month. Task 4 range reports must attach the tags for all covered months, in addition to their range key, so historical refunds expire the relevant report.
- The checkout route uses the existing same-origin JSON boundary and managed Vercel rate-limiting pattern. Its common implementation was extracted into `requireRequestRateLimit`, retaining existing auth rules, messages and fail-closed behavior. Donations have a separate `umunara-donation-checkout` rule and enable flag. Webhooks use signature authentication and are not subject to browser CSRF or checkout limits.
- Provider errors are safe 503 responses; ledger failures propagate for retry. Only normalized allowlisted snapshots reach the repository. No raw payload, PII, card/bank details, keys or signatures are logged or persisted by this implementation. All credentials and SDK construction are server-only. Existing check/PayPal giving behavior is preserved.

### Failed/cancelled refund rollout limitation

The adapter handles `charge.refunded` but does not map `refund.failed`, `refund.updated`, or refund cancellation/reinstatement events into Task 1's explicit `correctsProviderEventId` correction envelope. If a refund was previously recognized and subsequently fails or is cancelled, the provider's cumulative refund amount may decrease. An ordinary success snapshot cannot restore those funds: Task 1 intentionally treats regressive refund totals as stale. Therefore net giving can remain understated until an authorized provider-verified correction is ingested through a future correction workflow. Operators must reconcile these exceptional refund lifecycles before relying on totals; do not interpret a webhook's 200 acknowledgement as evidence of restored funds. This round documents the limitation without adding an incomplete reinstatement implementation or rewriting history.

Current official references rechecked: [Balance Transaction fields](https://docs.stripe.com/api/balance_transactions/object) distinguish transaction creation from funds availability, and the [Invoice object](https://docs.stripe.com/api/invoices/object) exposes `status_transitions.paid_at`; installed SDK declarations confirm both timestamp fields and invoice nullability.
