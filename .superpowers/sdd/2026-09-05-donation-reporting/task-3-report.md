## Implementation decisions

- No new dependency. The server uses OAuth client credentials and native fetch against fixed live/sandbox API origins, with no redirects, no caching of provider responses, ten-second request timeouts, safe errors, and provider request IDs for creation/capture. Secrets are server-only. PayPal setup is independent of Stripe configuration.
- Strict input permits only integer minor-unit amounts ($0.50–$999,999.99), USD, and cadence. The server generates a UUID and stores immutable amount/currency/cadence in PayPal `custom_id`. Neither arbitrary return URLs nor browser-supplied identity/payment state are accepted.
- Recurring giving uses preconfigured server plan IDs. Before creation the server verifies an active, unlimited, single regular monthly/yearly cycle, no setup charge, tax, or quantity pricing. The server overrides the fixed price per subscription and disables automatic outstanding-balance billing. No product or plan creation is implemented or performed.
- The browser posts only to `/api/v1` and navigates to validated PayPal hosted approval. This uses a hosted approval URL plus ID instead of loading PayPal's browser SDK; no public SDK configuration is needed. Browser JavaScript receives no credential, ledger state, or capture capability. The existing standalone PayPal form on the giving page is replaced by integrated giving; mailed giving and Stripe remain available.
- An order-bound HMAC capability expires after 15 minutes and lives in an HttpOnly, SameSite=Lax cookie (Secure on HTTPS). Capture requires this capability, same-origin JSON, managed donation rate limiting, and revalidation of the server-owned order/intent. Return query parameters merely display an explicit capture button. Neither redirect nor capture API response records financial success. Only verified webhooks do so. Creating another order replaces the prior cookie; expired/lost capabilities require restarting checkout.
- Webhook verification validates bounded JSON syntax and required header presence, then embeds the exact original raw JSON as PayPal's `webhook_event` value. It never reserializes that nested payload. Header values and configured webhook ID are sent to the fixed PayPal verification endpoint; only `verification_status: SUCCESS` permits normalization/provider reads/ledger writes. Certificate URLs are restricted to PayPal HTTPS certificate paths, and are never fetched by the application. Invalid signatures/payloads are not logged or persisted. Parsing syntax before verification performs no business action; event dispatch occurs only after verification.
- Supported financial events: `PAYMENT.CAPTURE.COMPLETED`, `.PENDING`, `.DENIED`, `.REFUNDED`, `.REVERSED`; `PAYMENT.SALE.COMPLETED`, `.REFUNDED`, `.REVERSED`; and `BILLING.SUBSCRIPTION.PAYMENT.FAILED`. Unsupported lifecycle events, including subscription activation, are acknowledged without financial writes. Recurring sale IDs own the initial gift and renewals, avoiding subscription-activation double counting.
- Settlement timestamps use `resource.update_time` from the verified completed capture/sale snapshot, preserving the actual completed transition rather than order/subscription creation. Pending/denied capture references use `unsettled:<capture-id>` and attempt creation time. Failed renewals use `unsettled:<subscription-id>:<failed-payment-time>` and the verified failure's amount/time. These remain zero-recognized audit projections. Reports must exclude unsettled statuses, consistent with Task 2.
- A narrow server repository lookup scoped to provider `paypal` and exact reference reads the original gift for adjustments. It validates the row, normalizes PostgreSQL timestamp offsets to canonical UTC, and retains immutable receipt/gross/currency/cadence/donor identity. A refund/reversal received before completion returns safe retryable 503 rather than inventing a receipt date. Duplicate/stale handling remains the atomic RPC's responsibility; there is no process-local production event deduplication or read/modify/write refund increment. Only applied events invalidate the receipt's UTC month tag.
- Capture refunds use verified cumulative `seller_payable_breakdown.total_refunded_amount`; they never add an individual refund amount to a stale read. Full refunds and reversals retain known fees and may produce negative net giving. Old ordinary success events preserve existing financial state and cannot silently reinstate reversed/refunded money. Task 1 correction semantics remain intact; no correction is invented from a success notification.

## Limits and rollout requirements

- No PostgreSQL/pgTAP test ran. The unavailable isolated temporary database was not retried, waited on, reset, or restarted. No migration was created or edited. The real client is exercised against HTTP fixtures, not PostgreSQL transaction/RLS/concurrency semantics. Follow the exact approved isolated pgTAP workflow in `task-1-report.md` when `/private/tmp/umunara-core-platform-task3.Lch2gq` is healthy and both donation migrations are applied.
- No real PayPal sandbox/live account was contacted. Before enabling actual giving, validate real Orders, plan overrides, subscription sale payloads, permission scopes, webhook signature verification, retries and settlement/fee behavior in an authorized PayPal sandbox. The public documentation marks subscription `application_context` deprecated but still exposes it for approval URLs; verify current account compatibility before rollout.
- Required private runtime configuration: `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`, explicit `PAYPAL_ENVIRONMENT=sandbox|live`, `DONATION_APPLICATION_ORIGIN`, and the existing server database credentials. Recurring giving additionally needs `PAYPAL_MONTHLY_PLAN_ID` and `PAYPAL_YEARLY_PLAN_ID` meeting the validated constraints. Configure the listed webhook events, the existing `umunara-donation-checkout` managed firewall rule and trusted ingress, and `DONATION_RATE_LIMIT_ENABLED=1`. No environment file was read or changed and no external configuration was performed.
- Exceptional refund lifecycles intentionally fail safely: partial subscription sale refunds lack a verified cumulative refund amount in this adapter and return 503; capture refunds returning nonzero fees require a cumulative fee reconciliation workflow and also return 503. Full sale refunds with a verified full amount are supported. Missing settlement timestamps/fees, unsupported currency conversion, changed intent amounts, and combined outstanding renewal amounts similarly return 503 with no ledger write. Operators must reconcile these exceptions; repeated retries alone cannot resolve an unsupported financial shape.
- Dispute fees and refund failure/cancellation/reinstatement are not inferred. A later verified correction workflow must supply Task 1's explicit `correctsProviderEventId`; ordinary success cannot reduce refund totals or restore a reversal. As in Task 2, totals can remain understated until these exceptional restorations are reconciled. No history is rewritten. The implementation does not claim complete exceptional-lifecycle reconciliation.
- The capture capability's HMAC is domain-separated using the server PayPal secret; rotating that secret invalidates outstanding 15-minute capabilities. No raw donor/card/bank payload or credential is persisted. No push or deployment was performed.
